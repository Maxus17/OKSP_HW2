# ДЗ 2 — инструкция нагрузочного испытания

Репозиторий: https://github.com/Maxus17/OKSP_HW2

Документ описывает параметры теста и порядок воспроизведения испытания. Индивидуальные результаты запуска сохраняются локально в `results/hw2/`.

## Стенд

Используется сервис библиотеки из ДЗ 1: Python, Flask, psycopg и PostgreSQL. Версии закреплены в Dockerfile и requirements.txt. Приложение запускается одним процессом Flask с потоками. Каждый запрос создаёт собственное подключение к БД.

```bash
git clone https://github.com/Maxus17/OKSP_HW2.git
cd OKSP_HW2
cp .env.example .env
```

В локальном `.env` задайте персональный префикс и собственные пароли. Префикс должен состоять из строчных латинских букв и подчёркиваний. Значения паролей в публичном примере пустые.

```bash
docker compose -f compose.yaml -f compose.hw2.yaml up -d --build app db
docker compose -f compose.yaml -f compose.hw2.yaml exec app python -m pytest -q
docker compose -f compose.yaml -f compose.hw2.yaml run --rm --no-deps k6 version
```

Учётная запись API — `librarian`. Basic Auth передаётся в каждом запросе. Отдельной операции login нет: setup выполняет авторизованную проверку готовности, исключённую из целевых метрик.

## Профиль нагрузки

Тест `load/test.js` поддерживает два отдельных режима:

- `mixed`: операции по фиксированным весам;
- `heavy`: только GET /api/summary.

Веса ниже — настройки сценария, выведенные из предполагаемых действий библиотекаря.

| Операция | Вес, % | Обоснование |
|---|---:|---|
| Список выдач | 30 | Регулярный просмотр журнала |
| Список просрочек | 15 | Проверка задолженностей |
| Карточка выдачи | 30 | Проверка читателя, книги и срока |
| Выдача | 10 | Запись выполняется реже просмотра |
| Возврат | 10 | Возвраты уравновешивают выдачи |
| Сводка | 5 | Периодический контроль показателей |

Общая сумма — 100%. На коротких ступенях фактические доли могут отличаться; ответы сохраняются по операциям.

## Модель и порог

Используется открытая модель constant-arrival-rate. Одна итерация отправляет один запрос, sleep отсутствует.

Заданные настройки:

- длительность ступени по умолчанию — 30 секунд;
- 100 preAllocatedVUs, 400 maxVUs;
- p95 целевого времени ответа < 500 мс;
- доля неожиданных ошибок < 1%.

Частота, длительность и лимиты VU задаются параметрами. Время ответа — k6 response.timings.duration. Допустимые статусы и структура JSON проверяются отдельно. Код 409 разрешён только для выдачи и возврата при наличии JSON error; такие конфликты считаются отдельно в business_conflicts.

## Подготовка данных

Перед каждой ступенью run_step.py восстанавливает учебные таблицы через seed.py work и запускает prepare.py. Наполнение задаётся генератором: 3000 читателей, 10000 книг, 30000 экземпляров, 50000 выдач. Подготовка добавляет 200 тестовых читателей без просрочки и сохраняет fixtures.json.

Подготовка удаляет ручные изменения учебных выдач. Применяйте её к выделенному учебному стенду.

Перед новым наполнением скрипт ждёт три отсчёта простоя: CPU приложения и БД ниже 25% одного ядра и отсутствие активных запросов. Режимы и ступени выполняются последовательно.

## Лестницы нагрузки

Начните каждый режим отдельно с небольшой частоты и затем удваивайте её:

```bash
python3 load/run_step.py mixed 2
python3 load/run_step.py mixed 4
python3 load/run_step.py heavy 2
python3 load/run_step.py heavy 4
```

Продолжайте каждую лестницу до первого нарушения порога или появления dropped_iterations. Последняя полностью доставленная ступень перед нарушением — допустимая интенсивность среди проверенных частот. При пропусках заявленный поток доставлен не полностью.

Скрипт выводит p50, p95, максимум, ошибки, пропуски и фактическую частоту. effective_rps учитывает полную длительность k6, включая завершение запросов. Не делите число завершений автоматически на длительность окна подачи.

## Сбор ресурсов и профиль

monitor.py использует поток docker stats и постоянное подключение psql. Период сбора — две секунды. Сохраняются CPU, память, PIDs, все клиентские соединения, активные запросы и ожидания блокировок. Наблюдатель исключён из счётчиков соединений.

Профиль снимайте отдельно на частоте излома тяжёлой операции. В примере ниже 2 — демонстрационное значение параметра; замените его своей найденной частотой.

```bash
python3 load/run_step.py heavy 2 --profile
```

py-spy записывает speedscope с потоками и --idle в течение 15 секунд на 10 Гц. Параметр --profile-rate меняет частоту. Путь внутри приложения — /app/results/hw2/. Успешность проверяется по profiler_exit_code и непустому profile.speedscope.json.

Профилированную ступень рассматривайте отдельно от основной лестницы: профилировщик добавляет расходы. --idle включает ожидающие потоки; доли снимков не равны загрузке CPU. analyze.py отдельно считает доли относительно стеков обработчика summary.

## Анализ

После завершения нагрузки:

```bash
docker compose -f compose.yaml -f compose.hw2.yaml exec app python load/explain.py
python3 load/analyze.py
```

Сохраняются read-only EXPLAIN (ANALYZE, BUFFERS), индексы, steps.csv, графики p95, статусы ответов и hot-functions.json при наличии профиля. Исходные JSON и журналы сохраняются.

Для отчёта подготовьте таблицы обеих лестниц, графики p95, временные ряды ресурсов, профиль с долями и местами вызова в собственном коде, проверку гипотез ДЗ 1 и направление оптимизации. Вывод об ограничивающем ресурсе должен опираться на полку временного ряда, совпадающую с изломом. Сведения о машине, дата и фактический коммит каждой серии берутся из своего запуска.

.env, результаты испытаний и локальная история Git исключены из публичной поставки.
